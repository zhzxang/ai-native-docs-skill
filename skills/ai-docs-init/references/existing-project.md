# 已有项目接入、迁移与升级

## 盘点与检查基线

先读取目标项目适用的根目录、docs 和局部执行约定，保留当前分支及其他执行者的修改。使用 `bootstrap.py --scan` 取得文件盘点，再阅读相关原文件；盘点结果不替代语义判断。

搜索整个仓库的已有文档与引用，包括根 README、设计或决策目录、`docs/contracts/`、API 文档、源码旁说明、归档和非 `docs/` 路径；不能只搜索新注册表的路径。检查旧 YAML front matter、紧凑条目、稳定 ID、状态、生效版本、证据和附件。只读需要的资料，不递归加载整库，不将模板、生成物或导航计作业务条目。

已有可运行的文档检查器时，在变更前保存其真实结果和使用版本；运行前检查实现及行为。没有兼容检查器、旧格式未知或无法执行时，记录具体未验证范围。变更后比较基线：本次引入的缺陷需修复；保留的历史缺陷需准确报告。不要用“检查通过”掩盖未被检查的旧格式。

代码位置和命令从项目实际资产核验，不为适配系统移动源码或批量运行发现的脚本。命令名为 `test`、`build` 或 `lint` 不能证明安全性；登记项目命令与执行核验是两个动作。

## 接入入口与处理冲突

先接入协议，让后续写入有明确入口。根 README、根 AGENTS、docs README 和 docs AGENTS 中的项目内容保留，系统指引通过明确托管区块合并。检查区块与原约定是否兼容：托管标记只界定更新范围，不自动解决旧约定与新协议的矛盾。

例如旧约定要求“每个功能单独建目录”，新协议要求前两条聚合存储，应列出冲突位置及建议的新写入约定，保留现有条目布局；不能同时留下互相矛盾的入口并宣称接入完成。用户已授权迁移或更新对应约定时，完成范围内合并；缺少必要裁决时继续兼容的独立变更，报告尚未完成的入口。

工具保护同名非托管文件、局部修改和非兼容配置。不要删除原文件来消除安装冲突，也不要为了通过检查关闭类型、降低最低内容、拆分阈值或批准要求。

## 历史迁移

迁移应在同一个可审查变更内保全内容并修复定位，依次处理一个明确领域或对象集合。安装任务没有自动授予重写全集、删除历史或改变已批准规范的权限；用户已明确授权的迁移范围可直接完成。

1. 依据匹配版本 Skill 的 `writing-policy.md`、`collections.json`、`conventions.md` 与 `lifecycle.md`，结合本项目 `docs/.ai-docs.json` 的覆盖确认类别、独立对象边界和状态映射。搜标题、关键词、ID、范围与版本查重；同对象更新既有条目，不产生“完善版”副本。
2. 记录迁移映射：旧文件及锚点、原 ID、新位置及锚点、状态或格式变化理由、附件与入链影响。小规模映射可放在变更说明；跨阶段迁移保存在任务或计划条目中，避免创建无人维护的第二份索引。
3. 保留原 ID 和完整正文、元数据、范围、依据、批准、生效及发布历史。字段不能直接映射时先记录原值及待裁决原因，不以重写消除问题。没有元数据且有效性未核验的材料使用 `status: draft`，未知字段按 schema 留为 `null`，并说明来源和待确认项；不要发明 `status: unknown`。原材料已经发布、生效或获批的已知事实仍须保留，不能因格式迁移把历史改写成“从未批准的草稿”。能核验的状态依据真实批准和生命周期映射，没有充分依据不能标为 active。
4. 按实际独立条目数选择布局：此前未展开的集合 1–2 条用紧凑文件，第 3 条完整展开；已展开集合即使仅 1–2 条仍保留目录。不要为了统一新样式收拢旧目录。每条有自己的元数据和状态，不能继承文件级公共批准。
5. 修复仓库全部相关入链、旧锚点、正文相对出链、附件引用、路由、替代关系和确有需要的派生索引。稳定 ID 不会自动修复链接。保留原附件和历史所需材料；外部无法直接修复的旧链接记录待处理项。
6. 在已授权的迁移范围内完成旧正文替换或移除，使一个对象只有一个可编辑权威来源。必要的旧入口可留下 `<!-- doc-redirect -->` 薄跳转，只包含迁移说明、旧 ID 锚点和新链接，不保留正文或条目元数据。未获授权、权威来源有歧义或映射未解决时保留原文并暂停该项迁移，不把复制出的第二份正文作为最终成果。
7. 核验迁移前后内容与事实无遗漏、无无依据变更，再运行兼容的结构和引用检查。已批准、生效政策及定价按生命周期要求保留历史版本与替代关系。检查器不能识别的旧格式明确报告未验证，不能宣称全集维护完成。

安装本身不需要迁移全部历史。尚未迁移的资料保留原位置，登记真实定位及接入缺口；必要时通过项目入口明确新写入规则和旧资料的适用范围。若新检查器因已存在的旧格式失败，应列出基线与迁移计划，不静默排除这些文档或将失败写成成功。

## 轻量升级与旧完整安装转换

轻量项目使用 `docs/.ai-docs.json` 中的 `system.version` 和 `installation`，升级只更新依赖声明与可兼容托管区块，保留其他项目字段、扩展字段和业务内容。托管区块之外的内容继续属于项目；根入口和 docs 入口不得继续要求项目拥有系统资源目录。

旧完整安装的 `docs/_system/project-map.json`、`commands.json` 先保全迁入新配置；与 Skill 默认值不同的兼容分类、路由保留在 `overrides`。旧配置中的扩展信息必须保留，不以字段精简丢弃事实。格式不兼容时先阻断对应转换，明确迁移，不能混装语义。

旧 `docs/_system/installation.json` 提供实际所有权与哈希基线。仅删除可证明由旧安装拥有、未修改且仍可安全移除的通用资源；入口、正文、附件或其他保留材料仍引用的资产应先处理引用再移除。未知所有权、当地修改或未解决引用的材料保留并报告，不整目录删除，不伪造基线。保存计划中的删除项同样须审阅，应用时验证哈希，失败回滚。

没有旧清单时，先接入轻量入口并保存配置，不把旧目录自动当作可删安装资产。逐项核验格式、事实、引用与归属，再在授权范围内迁移或合并。未处理的旧资源明确列为保留范围；目标日常写入以新配置和匹配 Skill 为准，不维护两份活动配置。

配置 schema、工具和协议需一起核验兼容性，不能只换新 JSON。项目定制与新版本都应保留的内容按字段或区块合并；冲突无法裁决时保留原文件，说明所需决定。依赖资源或入口不兼容时，状态是部分应用或受阻。修复后重跑计划和检查，确认重复执行不会制造副本。

升级完成还需报告项目配置与 strict 结果；安装版本最新不等于项目已就绪。`maintenance` 仅在已声明的事实、核验、权限和交接条件满足后启用，不由升级动作自动切换。
