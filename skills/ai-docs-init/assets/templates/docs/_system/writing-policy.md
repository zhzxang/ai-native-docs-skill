# 文档写入协议：分类固定，文件按需，第三条展开

本协议适用于所有项目知识写入：新增、修改、导入、需求、研究、反馈、成本、运行记录、开发回写和交接。纯聊天回答、暂存草稿和工具缓存不必强制归档。先判断是否确实需要长期检索、复用、执行、核验或交接，再决定持久化。

完整架构是分类词典，实际结构只服务已存在的内容。逻辑类别不随单文件与目录切换改变。最小结构仍保留产品、研究、运维等分类边界，不把无关内容塞进统一 `notes.md`。

## 1. 所有写入使用同一流程

1. 显式读取本协议、`collections.json`、根 AGENTS.md 与 docs/AGENTS.md；匹配任务路由，确认适用权限与事实来源。
2. 判断是否需要持久化，选择信息角色和已登记逻辑类别。注册表的 `unit` 定义该类别的独立维护单位，`minimum_content` 定义最低充分内容。
3. 用类型、ID、标题、关键词及关系查找已有同主题条目，同时核验适用范围、版本、状态与替代关系。未命中标题不等于不存在同一对象。
4. 已有对象更新原条目；确实是新对象才分配全库唯一 ID。原始反馈写入证据类别；采纳后的结论在获得适用授权后更新规范，不能自动提升证据的权威。
5. 按写入后的独立条目数选择紧凑写入或展开迁移，使用该类型的最小充分内容。完成工具创建的草稿时填写摘要和适用范围，以真实内容替换章节中的写作指令，移除“集中参考源”用途说明和不适用的空章节；影响正确性、授权或验收的未知仍保留，不把占位符或写作指令当作事实提交。
6. 核验关系与唯一来源，修复链接、锚点、路由和必要索引。运行结构检查以及与实际变更相称的验证，再说明真实结果和未验证项。

所有类别都先查找再新增；“补充收藏边界”应更新原功能，不新增“补充版 / 完善版 / 最终版”。不得为本次写入方便而擅自新增分类、改变阈值、降低批准或检查要求。

## 2. 什么是一个条目

一个条目是可以独立命名、检索和维护的对象，具体边界按注册表 `unit` 判断。通常具有独立范围、状态、验收或证据；是否独立仍需要语义审查，工具不能替代判断。

| 内容 | 条目数 | 触发展开 |
|---|---:|---|
| 一个功能的背景、规则、验收和多段分析 | 1 | 否 |
| 登录和收藏两个独立功能 | 2 | 否 |
| 登录、收藏、搜索三个独立功能 | 3 | 是 |
| 同一个 Bug 修改三次 | 1 | 否 |
| 三个不同 Bug，即使类型相同 | 3 | 是 |
| 同一反馈增加三段分析 | 1 | 否 |
| 三条可以独立处理的反馈 | 3 | 是 |

标题数、章节数、段落数、字段数、验收条件数、引用数、编辑次数和文档长度都不是条目数。复杂对象的必要附录不自动成为新对象；确需独立维护时说明信息边界并遵守相应分类。

## 3. 路径与集合状态机

`collections.json` 保存 `key`、`base_path`、`prefix`、`unit`、`minimum_content` 和集中模板路径，不保存易过期的 `item_count`。条目数由当前源记录计算，模板、导航与派生索引不计数。默认 `compact_max_items` 为 2，这个阈值是本项目规则。

| 集合状态 | 物理结构 | 写入动作 |
|---|---|---|
| 没有内容 | 没有业务文件或集合目录 | 不预建空壳 |
| 第 1 个独立条目 | `<base_path>.md` | 创建聚合文件和逐条元数据 |
| 第 2 个独立条目 | 仍为 `<base_path>.md` | 追加独立条目，状态和证据不共用 |
| 第 3 个独立条目 | `<base_path>/` | 迁移全部旧条目并新增第三条 |
| 已展开 | `<base_path>/<ID>-<slug>.md` | 更新或新增对应条目文件 |
| 已展开后仅剩 1–2 条 | 仍保留目录 | 不自动收拢或反复移动路径 |

例如 `feature` 的基础路径是 `docs/product/features`：前两条存于 `docs/product/features.md`；第三条出现后迁移到 `docs/product/features/FEAT-001-login.md` 等文件。`product/` 是业务分类目录，`features/` 才是受阈值控制的集合目录。

新增集合类别只登记分类规则，不立即建空文件、目录、README 或模板实例。出现实际内容后才创建必要的父分类目录。已展开集合不因删除、归档或筛选减少条目而自动收拢；改变此行为属于独立、明确授权的存量整理。

一个集合只保留一种可编辑正文来源。聚合文件与目录不能同时保存正文。集合展开后不为每个条目再建 `slug/index.md`，不同时创建 README、index、overview 多份导航；已有总索引或定位工具足够时不增加导航，确需入口时只建一个薄导航。

## 4. 最小充分内容与事实边界

每个条目至少能回答：它是什么、适用哪里、具体内容是什么、依据或核验条件是什么。按注册表保留类型特有的最低内容，可省略确实不适用的可选章节，不统一删成三行，也不复制尚无信息的大量空章节。

| 类型 | 最低需要保留 |
|---|---|
| 功能 | 范围、关键行为规则、可验证的验收条件、来源与关联 |
| 用户反馈 | 脱敏来源、时间、原始观察；观察与推断分开 |
| ADR | 背景、决策、理由、后果和决策状态 |
| 工作项 | 目标、范围、验收、唯一执行状态、必要交接 |
| Runbook | 触发条件、权限边界、步骤、验证和失败处理 |
| 测试报告 | 对象、环境、实际结果、证据和未验证项 |
| 成本 | 周期、币种、实际与预算的区别、来源和统计口径 |
| 定价或政策 | 适用范围、生效版本、规则、批准和发布状态 |

不能为了精简删去影响正确性、权限或验收的未知项。关键未知明确标记并说明影响；例如取消订阅后本周期权益未确定，仍须保留待确认事项。`verified_at` 只记录实际核验，`approval_ref` 只指向真实批准或适用预授权，不因编辑或拆分刷新。

任务执行状态 `state`、文档有效状态 `status`、版本发布状态 `release_state` 分开；多个条目共享文件不代表它们共享状态。代码实现、规范批准、任务完成、发布和生产验证是不同事实。

## 5. 紧凑条目格式

聚合文件有一个集合标题。每个条目依次包含显式小写 ID 锚点、二级标题、紧随其后的 `yaml doc-meta` 代码块和三级内容标题。元数据采用 [conventions.md](conventions.md) 的完整扁平字段规则，不允许只有聚合文件的公共元数据。

````markdown
# 功能需求

<a id="feat-001"></a>
## FEAT-001 · 收藏

```yaml doc-meta
id: "FEAT-001"
slug: "bookmarks"
type: "feature"
status: "draft"
summary: "收藏对象的范围、行为与验收。"
owner: null
applies_to: null
verified_at: null
verification_ref: null
authority: "normative"
approved_by: null
approval_ref: null
```

### 范围与规则
记录已确认的范围和行为规则；关键未知明确保留。

### 验收
记录可检查的条件及未确定条件。

### 依据与关联
记录需求来源、相关 ID 与实际链接。
````

`doc-meta` 是本项目工具支持的格式，不是所有 Markdown 工具的通用标准。字符串用双引号，未知为 `null`；`slug` 是该条目的英文短名，展开用它形成稳定文件名；任务、发布等类型还保留各自专属字段。展开时转换为独立文件的 YAML front matter，保留完整原字段及小写 ID 锚点，正文标题恢复独立文件层级；转换不改变身份、状态、适用范围或证据。

## 6. 第三条展开是一项完整迁移

在同一个可审查变更或隔离工作区内完成以下操作，并在最终检查点验证，不能把合法迁移的临时中间状态作为最终结果提交。

1. 保存已有条目 ID、完整元数据、正文、旧位置与新位置映射，确认第三条确是独立对象。
2. 创建 `<base_path>/<ID>-<slug>.md`，迁移旧条目并加入新条目；保留状态、范围、事实、证据和必要附件关系。
3. 修复指向旧聚合文件的入链及锚点，例如 `features.md#feat-001` 改为 `features/FEAT-001-login.md#feat-001`。稳定 ID 不会自动修复 Markdown 链接。
4. 重新计算迁移正文中的相对出链，以及附件引用、替代关系、手工路径和路由；集合 key 的逻辑归属不变。
5. 删除旧聚合正文，更新定位与必要生成索引。确有无法立即修改的外部旧链接时，可保留带 `<!-- doc-redirect -->` 标记的薄跳转页，只含迁移说明、旧 ID 锚点和对应新入口，不含原正文或 `doc-meta`，也不是可编辑集合源。此标记用于工具区分跳转与双份正文，不能用于隐藏实际记录。
6. 对最终布局检查元数据、ID 唯一性、阈值、双份来源、链接和锚点；核验条目内容无遗漏或无依据改变，再一起交付。

缺少旧条目元数据、无法确定权威来源或入链映射有歧义时，记录具体问题并解决后再完成迁移，不以重写或丢弃旧内容消除问题。重要历史、生效政策及定价版本还需遵守 [lifecycle.md](lifecycle.md) 的替代和保留要求。

## 7. 模板、初始化与定位

集合模板集中在 `docs/_templates/<key>.md`；单篇文档、导航、流程和适配器参考集中在 `docs/_templates/reference/`，未使用模板不实例化为业务目录。最小部署只安装根入口、docs 入口、规则配置、工具和集中模板源；项目总纲与其他业务文档有确认内容后才建立。

定位优先使用 `docctl.py find` 的类型、ID、关键词和状态过滤；`index` 同时覆盖聚合文件中的各独立条目和已展开文件，每条记录定位到对应锚点。路由用 `{"collection":"feature"}` 解析当前实际位置，尚无内容的类别只报告按需位置；不存在的按需单篇资料使用 `optional_path`，不为满足路由提前制造文件。

## 8. 检查与交付

执行 `python3 docs/_tools/docctl.py check`，并针对本次写入逐项确认：

- 分类与信息角色正确，已有同主题对象优先更新，ID 与实际条目边界一致。
- 没有无内容业务壳；未展开集合最多两个独立条目；第三条完成迁移；已展开未隐式收拢。
- 每条元数据完整且独立，文档、任务和发布状态未混用，正文满足类型最低内容，关键未知未隐藏。
- 只有一个可编辑来源，ID、证据和关系未丢失，入链、相对出链、锚点与必要索引一致。
- 事实、核验、批准和上线声明都有对应依据，所需检查真实执行，未验证项明确。

结构检查只能判断声明与文件是否符合协议，不能单独证明两个对象确实独立、分类正确、外部来源仍有效或生产行为符合规范。自然语言入口也不是权限控制；受保护分支、CI 必需检查、受控写入工具和文件访问边界需要项目实际配置。工具存在不代表这些强制机制已启用，有直接文件写入能力也不能宣称入口不可绕过。

只有必要回写、迁移和验证完成后才能按 [definition-of-done.md](definition-of-done.md) 宣称维护完成；受阻时保留可审查成果、真实检查和剩余事项，不擅自降低分类、阈值、批准要求或门禁。
